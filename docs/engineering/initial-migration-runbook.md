# Initial database migration — implementation instructions

The Prisma schema exists, but **the initial migration has not yet been generated or tested**. Do not hand-write a migration and claim it was generated by Prisma.

## On a developer machine with Docker and pnpm

```bash
git checkout chore/sprint-0-hardening
pnpm install --frozen-lockfile
docker compose up -d postgres redis
pnpm db:generate
pnpm --filter @academy/database exec prisma validate
pnpm db:migrate:dev -- --name init_foundation
```

Set `DATABASE_URL` in your local environment using `packages/database`'s documented configuration before running Prisma commands. Never commit `.env` files or credentials. If the forwarded `--` argument is incompatible with the workspace script, run `pnpm --filter @academy/database exec prisma migrate dev --name init_foundation` directly.

Commit the resulting `packages/database/prisma/migrations/<timestamp>_init_foundation/migration.sql` and `migration_lock.toml`.

## CI acceptance checks to add after migration is committed

1. `pnpm --filter @academy/database exec prisma migrate deploy` against the CI PostgreSQL service.
2. `pnpm --filter @academy/database exec prisma migrate status`.
3. `pnpm --filter @academy/database exec prisma migrate diff --from-migrations packages/database/prisma/migrations --to-schema-datamodel packages/database/prisma/schema.prisma --exit-code` using a configured shadow database URL where required; verify exact CLI compatibility with the pinned Prisma 6 version.
4. Integration tests must create two tenants and prove that the application never reads or modifies tenant B's data when authenticated as tenant A.
5. Test that deleting a tenant with audit records fails, and test append-only protections once implemented.

## Important
A successful schema validation is not proof that migrations run. No runtime checks have been executed by this document.
