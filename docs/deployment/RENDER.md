# Deploying to Render

The project runs as three independent parts, each of which can be built, started and scaled on its own:

| Part     | Where                              | Code                            | Talks to                                  |
| -------- | ---------------------------------- | ------------------------------- | ----------------------------------------- |
| Web      | Render web service `sportexus-web` | `frontend/` (Next.js 15)        | the API, through its own `/v1` proxy only |
| API      | Render web service `sportexus-api` | `backend/` (NestJS 11)          | the database and Redis                    |
| Database | Neon PostgreSQL                    | `packages/database/` (Prisma 6) | -                                         |
| Redis    | Render Key Value `sportexus-redis` | -                               | rate limits shared by all API instances   |

The browser only ever calls the web app's own origin (`/v1/...`), so cookies are first-party and there is no
cross-origin request from the browser. The web app forwards to the API with a shared secret (`INTERNAL_PROXY_SECRET`)
that lets the API trust the real client IP for rate limiting.

`render.yaml` (repository root) describes all three Render resources.

## Trusted origins per environment (S2)

`CORS_ORIGIN` on the API lists the exact web origins that may send cookie-authenticated requests (CSRF check). No
wildcard is accepted in production.

| Environment | `CORS_ORIGIN`                                                                               |
| ----------- | ------------------------------------------------------------------------------------------- |
| Development | `http://localhost:3000`                                                                     |
| Production  | `https://<web service>.onrender.com` (and a custom domain if one is added, comma-separated) |

## First deployment

1. **Database (Neon).** The production database must be a separate Neon project or branch with its own data. Create
   the runtime role **before the first deploy**, because the migrations grant it its privileges: run
   `packages/database/scripts/provision-runtime-role.sql` as the owner (it only creates `sportexus_app`; replace the
   password placeholder in a local copy, never commit it), or create the role in the Neon console. A role created
   after the migrations gets no privileges until the privilege migrations are re-applied.
2. **Blueprint.** In Render: _New → Blueprint_, pick the repository and the branch in `render.yaml` (`main`).
3. **Secrets** (Render dashboard → each service → Environment):

   | Service         | Variable                            | Value                                                                    |
   | --------------- | ----------------------------------- | ------------------------------------------------------------------------ |
   | `sportexus-api` | `DATABASE_URL`                      | Neon **pooled** URL as `sportexus_app`, ending `&connect_timeout=15`     |
   |                 | `DATABASE_ADMIN_URL`                | Neon **direct** connection string as the owner (used only by migrations) |
   |                 | `CORS_ORIGIN`                       | `https://<web service>.onrender.com`                                     |
   |                 | `NEXT_PUBLIC_APP_URL`               | `https://<web service>.onrender.com` (links in e-mails)                  |
   |                 | `RESEND_API_KEY`, `MAIL_FROM_EMAIL` | e-mail provider                                                          |
   | `sportexus-web` | `INTERNAL_API_URL`                  | `https://<api service>.onrender.com`                                     |

   `JWT_SECRET` and `INTERNAL_PROXY_SECRET` are generated by Render; the web app receives the same proxy secret
   automatically.

4. **Deploy.** The API build runs `prisma migrate deploy` with `DATABASE_ADMIN_URL`. If a migration fails, the deploy
   fails and the previous version keeps serving. The API refuses to start in production when `DATABASE_URL` is a
   superuser, a role that bypasses row-level security or a table owner.
5. **Check.** `https://<api>.onrender.com/v1/health/ready` answers 200, then sign in on the web app.

## Notes

- Free Render services sleep when idle; the first request after a pause takes a few seconds.
- Never point the production services at the development database, and never commit connection strings.
- Local development is unchanged: `pnpm dev:backend` (port 3001) and `pnpm dev:frontend` (port 3000), each in its
  own terminal, with `backend/.env` and `frontend/.env`.
